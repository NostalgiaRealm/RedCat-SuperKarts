# Mobile performance

Date: 30 October 2026. This work targets the race on phones. Gameplay is
unchanged, and rendering is pixel-identical apart from one visible trade-off: a
lower automatic resolution on phones and tablets.

## Measured result

Measured with `tools/mobile-performance.mjs` on the Netherlands track: emulated
phones in headless Chromium 145, main thread throttled, software GPU. Budget is
the share of the main thread that updates and 60 Hz frames need together.

| Profile | Budget | Update | Frame | GPU drain | Live frames / updates per second |
| --- | --- | --- | --- | --- | --- |
| Portrait, 393×852 at DPR 3, 4× throttle | 119% → 24% | 19.9 → 3.1 ms | 6.6 → 2.0 ms | 22.6 → 5.6 ms | 13.5 / 6.9 → 60 / 30 |
| Landscape, 852×393 at DPR 3, 4× throttle | 92% → 23% | 15.7 → 3.0 ms | 4.8 → 1.9 ms | 15.5 → 5.6 ms | 18.7 / 9.5 → 60 / 30 |
| Budget phone, 360×800 at DPR 2, 6× throttle | 162% → 44% | 26.2 → 5.3 ms | 9.6 → 3.9 ms | 8.8 → 5.7 ms | 30.6 / 17.2 → 57 / 29 |

| Per race | Before | After |
| --- | --- | --- |
| Allocation per update | 3660 KiB | about 430 KiB |
| Vertex data uploaded per update | 136 KiB | 14 KiB |
| Draw calls per frame | about 320 | about 140 |
| Requests to load a race | 1514 | 221 |
| Transferred to load a race | 59 MB | 26 MB |
| Same, on the website with gzip | 59 MB | 15.4 MB |
| WAV requests for a second race on the same track | about 220 | 0 |

Gzip is a server setting, see [hosting](hosting.md#file-responses-and-caching); it is on
for this game on games.nostalgiarealm.com, for text and mesh data but not audio,
video or images.

Updates stop at about 30 per second in the table because of the throttling. The
same build without it reaches 37.5, against the game's limit of 40.

**Limits:** these are emulated phones and a software GPU, so compare the numbers
between builds; they do not predict a real phone's frame rate. No physical phone
or real Safari was measured. Reports:
[`evidence/mobile-performance`](../evidence/mobile-performance/).

## What changed

**Simulation (same results):**

- Kart physics, AI, collision, ground sampling and effects no longer allocate
  arrays and closures in their hot paths. Far-away collision candidates are
  rejected before the corner calculations.
- The scenery loop visits only placements with a callback, and motionless props
  skip recalculation.
- Ground sampling, which the kart shadow grid uses 405 times per update, no longer
  allocates and tests a bounding box before each triangle.
- The bundle no longer uses esbuild `keepNames`, which ran
  `Object.defineProperty` for every named closure created.

**Visuals and HUD:**

- Kart colours are written and uploaded only when they change. Ribbons
  and skidmarks upload only the vertices they use.
- HUD specs are no longer re-parsed every update, and HUD layout is measured only
  when it can have changed. Each text string is one draw instead of one per
  glyph, and consecutive HUD items share one render call.

**GPU:**

- At default settings the HUD is drawn directly into the world target, so a frame
  takes two full-screen passes instead of three. Paused redraws still never blend
  the HUD twice.
- Depth is discarded after use (`invalidateFramebuffer`), which saves memory
  bandwidth on the tile-based GPUs in phones. The canvas and the HUD composition
  surface no longer have depth buffers.
- Road batches that are neighbours in draw order and share a texture merge into
  one draw: about 114 road draws become about 5, with the same triangle order.
- Textures without colour-key pixels compile without `discard`.
- Normals, which no material reads, are no longer computed or uploaded.

**Phones and tablets (visible):** see
[Resolution on phones](more-settings.md#resolution-on-phones-and-tablets).

**Frame pacing:** a display frame now serves an update timer that is already
late, so a busy main thread does not draw while the update waits. The 25 ms
update gate is unchanged.

**Loading:**

- Meshes load from one binary pack, `src/mesh-pack.bin` (4.6 MB, generated by
  `npm run bundle`), instead of 1,241 JSON files. A test proves it holds exactly
  the values the JSON loader produces. `public/assets/meshes` stays the source
  and the fallback.
- The viewer keeps decoded sounds, so a following race only loads what it does
  not share with the previous one.
- Voice samples that no recovered request site can select are no longer loaded
  (`tools/validate-voice-audio.mjs` still checks them all).
- The touch bonus icon went from 1254×1254 (1.4 MB) to 320×320 (126 KB).
- Sound specs are looked up in a table instead of re-parsing `Sound.ini`.

## How exactness was checked

- `tools/race-trace.mjs` hashes the exact bits of karts, AI, camera, scenery,
  pickups, projectiles, rescue, effects, sounds and the random stream per update.
  `tests/race-trace.test.mjs` compares 8 scenarios on all six tracks with a
  reference from before this work, in the normal test suite.
- `tools/golden-frames.mjs` compares exact framebuffer hashes between builds.
  After the final change, all 42 frames from before this work matched on the
  Netherlands track, in the 800×600 and portrait touch layouts. Other tracks and
  the MSAA, render-scale and low-effects cases were not rerun in the browser.
- The full Node suite passes, including the original-instruction fixtures at both
  precisions. Browser tests passed for the HUD framebuffer, MSAA, touch controls,
  engine lights, Meer instellingen and streams, all in Chromium.
- WebKit 26 with iPhone emulation ran a race at the phone cap with no errors. A
  second race made no WAV requests and its sound played.

## Reproduce

```sh
node tools/serve.mjs &
node tools/mobile-performance.mjs --profile portrait --out report.json
node tools/golden-frames.mjs --only track-0 --compare frames.json
node tools/race-trace.mjs --compare trace.json
```

Create `frames.json` and `trace.json` first with `--out` on the build to compare
against.
